# Steering スキル

`.steering/` の3ファイルで「今回何をするか」を計画し、進捗と結果を残す。tasklist.md はユーザーが進捗を確認する正式な記録であり、作業内容と常に一致させる。

## モード1: 計画

1. `.steering/[YYYYMMDD]-[タスク名]/` を作成する（タスク名は英小文字のケバブケース）
2. `docs/` のうち今回の作業に関係するものを読む。テスト・lint などのコマンドは `docs/development-guidelines.md` に従う
3. `templates/` の3ファイルを元に requirements.md → design.md → tasklist.md の順で作成する。テンプレートのセクションは該当するものだけ残す
4. design.md の「docs への影響」で、次のいずれかを選び、理由を書く。選んだ結果に合わせて tasklist.md を組む

| 判定 | 進め方 | tasklist.md での位置 |
|---|---|---|
| 影響なし | steering → 実装 | docs 更新タスクなし |
| 仕様の変更（機能・CLI/API・データモデルなどの定義が変わる） | steering → docs → 実装 | **最初のフェーズ**で docs を更新し、それを正として実装する |
| 実装結果の反映のみ（構成や用語の追記など） | steering → 実装 → docs | 実装の後のフェーズで更新する |

tasklist.md には、今回の作業で完了させるタスクだけを、完了を確認できる粒度で書く。「将来検討」は requirements.md のスコープ外に書く。

## モード2: 実装

tasklist.md を最後まで自律的に進める場合（`/add-feature` など）は、開始時に `.steering/.active` を作成し、作業ディレクトリのパス（例: `.steering/20250115-add-user-profile`）を1行で書く。Stop hook がこれを見て、未完了タスクを残したままの終了を防ぐ。フェーズごとにユーザーの確認を取りながら進める場合は作成しない。

- タスクを**完了したら**、その都度 tasklist.md の `[ ]` を `[x]` にする。まとめて後から更新しない
- 計画と違う進め方をした場合は、該当タスクに注釈を付ける。設計が変わった場合は design.md も更新する
- 大きすぎるタスクは、サブタスクに分割して tasklist.md に追加してから進める
- 途中で必要になったタスクは tasklist.md に追加する
- タスクを実施しないのは、技術的に不要になった場合だけとする（方針変更で機能自体が不要になった、別の実装に置き換わった、など）。その場合は理由を残す:
  `- [x] ~~タスク名~~（不要: 具体的な技術的理由）`
  「時間がない」「難しい」は理由にならない。本当にユーザーの判断が必要な場合は、未完了のまま理由を説明して止まる

## モード3: 振り返り

1. 全タスクが `[x]` になっていることを確認する
2. tasklist.md の「実装後の振り返り」に、完了日・計画との差分・学んだこと・次回への改善提案を書く。差分がなければ「なし」でよい
3. `.steering/.active` があれば削除する
4. ユーザーに完了を報告する

## 補足

- 作業を中断して別の作業に移る場合や、`.steering/.active` が古い作業を指したまま残っている場合は、削除してよい（マーカーと tasklist.md がどちらも24時間以上更新されていなければ、hook は自動で無視する）。ただし、別のセッションがこの作業を進めている可能性がある場合は削除しない
