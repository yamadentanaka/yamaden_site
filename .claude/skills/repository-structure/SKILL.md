# リポジトリ構造定義スキル

アーキテクチャ設計で決めた技術スタックとレイヤー構成を、具体的なディレクトリ構成と配置ルールに落とし込む。新しいファイルをどこに置くかを、この文書だけで判断できる状態にする。

## 入力と出力

- 入力: `docs/product-requirements.md`、`docs/functional-design.md`、`docs/architecture.md`（いずれも必須）
- 出力: `docs/repository-structure.md`。構造は [template.md](template.md) に従い、該当しないセクションは削除する
- 既存の定義書がある場合は、その構造と内容を優先し、変更箇所だけを更新する

## このプロジェクトでの決め事

- ディレクトリ構成と命名規則は、採用した言語・フレームワークの慣習に合わせる（例: Rust の `src/` + `tests/`、Python の src レイアウト）
- 各ディレクトリは単一の役割を持つ。`utils/` `misc/` のような曖昧な置き場は作らない。共有コードは、本当に複数のレイヤーで使うものだけを共有用ディレクトリに置く
- architecture.md のレイヤーをディレクトリに対応させ、依存してよい方向・禁止する方向を書く。循環依存は禁止
- テストの配置場所と命名規則を決める
- `.steering/`（作業単位の計画）と `.claude/`（Claude Code の設定）は構成に含める。`.steering/` を git で管理するか（.gitignore の対象にするか）はプロジェクトで決め、既存の運用（作業の履歴としてコミットしている等）があればそれに従う。どちらの場合も、`.steering/.active`（`/add-feature` の実行中マーカー）は .gitignore の対象とする

## 品質基準

- [ ] 各ディレクトリの役割が明確
- [ ] レイヤーとディレクトリの対応、依存のルールが明確
- [ ] ソース・テスト・設定ファイルの配置先と命名規則が決まっている
- [ ] 機能が増えたときの分割方針（どの規模でサブディレクトリやモジュールに分けるか）がある
