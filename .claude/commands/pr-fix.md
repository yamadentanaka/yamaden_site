# レビュー対応（pr-fix）

GitHub の Pull Request に **投稿済みのフィードバック**（レビューツールが投稿した
コメント、および人間のレビュアーによるコメント・返信）を PR から取得し、
未対応の指摘をコードに反映します。引数で渡された PR の URL を対象に、以下の手順を
**順番に** 実行してください。

**コミット・push・インラインコメントへの返信は行いません。** 対応が完了したら
`/pr-fix-push <PRのURL>` を実行してください。

**このコマンドは、対象PRのリポジトリ内（カレントリポジトリ自身のPR）で実行することを
前提とします。** 他リポジトリのPRをcloneして解析する用途には対応していません。

## 入力

- 第1引数: **PR の URL**（必須）。例: `https://github.com/acme/web-app/pull/123`
- 第2引数: `suggestion`（任意）。指定された場合は 💡 提案 レベルの指摘も対応対象に含める
  （未指定時は 🚫 ブロッカー / 🤔 要検討 のみを対応対象とする）。

引数が渡されていない場合は、PR の URL を尋ねてから開始してください。

## 前提

- `gh` CLI が認証済みであること（`gh auth status` で確認可能）。
- ターミナルコマンドはワークスペースルート（このリポジトリ）で実行する。
- カレントディレクトリが対象PRのリポジトリであること。

## 手順

### 1. URL をパース
PR の URL から `owner` / `repo` / `pull_number` を抽出する。

### 2. 対象リポジトリであることを確認し、PR ブランチをチェックアウトする
- カレントリポジトリが対象PRのリポジトリと一致するか確認する。
  ```bash
  gh repo view --json nameWithOwner -q .nameWithOwner
  ```
  一致しない場合、「このコマンドは `<owner>/<repo>` のリポジトリ内で実行してください」
  と案内して停止する。
- 未コミットの変更がある場合（`git status` で確認）、ブランチ切り替えにより混在する
  おそれがあるため、事前にユーザーに確認する（コミット/stash/中断のいずれかを選ばせる）。
- 以下で PR ブランチに切り替える。
  ```bash
  git fetch origin --prune
  gh pr checkout <pull_number>
  ```
- **重要**: コードの修正はこのリポジトリ内で直接行う。

### 3. PR に投稿済みのフィードバックを取得する
GitHub 上の実際の投稿内容を正とし、以下をすべて取得する。

```bash
# インラインのレビューコメント（返信・在り処含む）
gh api repos/<owner>/<repo>/pulls/<pull_number>/comments --paginate

# 全体レビュー（サマリ本文・承認状態）
gh api repos/<owner>/<repo>/pulls/<pull_number>/reviews --paginate

# 通常のPR会話コメント（インラインでないもの）
gh api repos/<owner>/<repo>/issues/<pull_number>/comments --paginate
```

各インラインコメントについて、`id` / `path` / `line`（or `original_line`）/ `side` /
`body` / `user.login` / `in_reply_to_id` / `pull_request_review_id` を記録する。
`in_reply_to_id` が付いているものは既存スレッドへの返信であり、議論内容の把握に使う。

会話（スレッド）の解決状態を GraphQL で取得する（`isResolved: true` は対応不要）。

```bash
gh api graphql -f query='
  query($owner:String!,$repo:String!,$number:Int!){
    repository(owner:$owner,name:$repo){
      pullRequest(number:$number){
        reviewThreads(first:100){
          nodes{
            id
            isResolved
            comments(first:10){ nodes{ databaseId path line body } }
          }
        }
      }
    }
  }' -f owner=<owner> -f repo=<repo> -F number=<pull_number>
```

`reviewThreads[].id`（スレッドの node id）は手順6でスレッド解決に使うため保持しておく。

### 4. 対応対象を絞り込む
- レベル判定: コメント本文冒頭の絵文字ラベル（🚫 ブロッカー / 🤔 要検討 / 💡 提案 / 👍 GoodPoint）で判定する。
  ラベルが無い人間のコメントは、内容から重大度を推定する（不明な場合は 🤔 要検討 として扱う）。
- デフォルトの対応対象: **🚫 ブロッカー・🤔 要検討**。
- 第2引数に `suggestion` が指定された場合は **💡 提案** も対応対象に含める。
- 👍 GoodPoint は対応対象外。
- 対応する GraphQL の `isResolved: true` に該当するスレッドは既に解決済みとして除外する。
- 既に返信（`in_reply_to_id` あり）で「対応済み」等の言及があるコメントは、実コードの状態と
  照合し、実際に反映されていなければ対応対象に残す。
- 絞り込んだ一覧（件数・`path:line`・レベル・要約）をユーザーに提示する。

### 5. 対応方針を提示し、承認を得る
絞り込んだ指摘それぞれについて、該当ファイル・該当行の周辺を読み、指摘内容を理解した
上で **対応方針（案）** を作成する。

- 対応方針には「指摘内容の要約」「修正の方向性」「対象ファイル・箇所」を含める。
- 指摘内容が既に解消されている、または対応不能・対応不要と判断した指摘は、
  理由を明記した上で「スキップ」を提案する。
- 全指摘分の対応方針を一覧（`path:line`・レベル・対応方針 or スキップ理由）で提示し、
  **ユーザーの承認を得るまでコードの修正には着手しない。**
- ユーザーから修正・変更の指示があれば対応方針を更新し、再度提示して確認する。
  承認が得られなかった指摘は対応対象から外す。

### 6. 承認された対応方針に沿ってコードに反映する
チェックアウトした PR ブランチ上で、承認された指摘を1件ずつ処理する。

- 承認済みの対応方針に沿って修正を行う。複数の指摘が同一箇所に関係する場合はまとめて
  対応してよい。
- 実装中に、承認済みの方針から変更が必要だと判明した場合は、変更内容をユーザーに
  提示し再度確認を得る。
- 各指摘について「指摘内容 → 対応方針 → 実施した変更」を記録しておく（レポートに使う）。

### 7. 差分を確認する
`git diff` で変更内容を確認し、指摘に関係のない意図しない変更が
含まれていないか確認する。

### 8. 対応内容を提示し、次のステップを案内する
- 対応した指摘・スキップした指摘（理由付き）を一覧で提示する。

  | path:line | レベル | 対応内容 / スキップ理由 |
  | --- | --- | --- |
  | `path/to/file.ext:123` | 🚫 ブロッカー | <実施した変更の要約> |

- **この時点ではコミット・push・コメント返信は行わない。**
- 「変更をコミット・push し、対応したコメントに返信するには `/pr-fix-push <PRのURL>` を
  実行してください」と案内する。

## 注意

- このコマンドはカレントリポジトリ自身のPRを対象とする。他リポジトリのPRを
  cloneして解析する用途には対応していない（対象外の場合はその旨を伝えて停止する）。
- コードの修正は必ず PR ブランチ上で行い、`main`/`master` 等のデフォルトブランチを
  直接編集してはならない。
- **手順5で対応方針をユーザーに提示し、承認を得るまでコードの修正を行ってはならない。**
  無断で修正に着手しない。
- コミット・push・コメント返信・スレッド解決は行わない（`/pr-fix-push` の役割）。
- 対応方針・要約はすべて **日本語** で書く。
- `gh` が未認証・PR が見つからない・スレッド取得に失敗する等のエラー時は、
  原因と対処を提示して停止する。
