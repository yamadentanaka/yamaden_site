# 新機能の追加

引数の機能（例: `/add-feature ユーザープロフィール編集`）を、計画・実装・検証・振り返りまで自律的に進める。

**判断の原則**: 途中でユーザーに確認せず最後まで進める。docs から判断できない仕様上の分岐は、docs と既存の実装に最も沿う選択をし、その判断と理由を design.md に残して最終報告で明示する。止まるのは、どの選択でも手戻りが大きい場合や、破壊的な操作が必要な場合だけとする。

## 1. 計画

steering スキルのモード1で `.steering/[YYYYMMDD]-[機能名]/` に3ファイルを作成する。その前に、関連する docs と、既存の類似実装（命名・構成・テストの書き方）を確認する。

design.md の「docs への影響」の判定に従って tasklist.md を組む。仕様の変更なら、docs の更新を最初のフェーズに置く。

## 2. 実装

steering スキルのモード2で、tasklist.md の全タスクを完了させる（`.steering/.active` を作成する）。コーディング規約とコマンドは `docs/development-guidelines.md` に従う。

## 3. 検証

1. `docs/development-guidelines.md` に記載されたテスト・lint・型チェックなどを全て実行し、失敗があれば修正する
2. `implementation-validator` サブエージェントに、ステアリングディレクトリのパスと変更したファイルの一覧を渡して検証させる
3. 重大度が「必須」の指摘は修正し、1 を再実行する。「推奨」以下は妥当なものだけ反映し、見送ったものは理由を振り返りに残す

## 4. 振り返り

1. docs への影響が「影響なし」以外の場合は、tasklist.md の docs 更新タスクが完了し、docs が最終的な実装と一致していることを確認する
2. steering スキルのモード3で振り返りを記録する（`.steering/.active` を削除する）

## 完了条件

- tasklist.md の全タスクが `[x]`（技術的に不要になったものは理由付き）
- 開発ガイドラインのコマンドが全て成功している
- validator の「必須」の指摘が解消されている
- docs が実装と一致している
- tasklist.md に振り返りが記載されている

最後に、実装内容、docs の更新内容、自分で判断した仕様上の選択、見送った指摘を簡潔に報告する。
